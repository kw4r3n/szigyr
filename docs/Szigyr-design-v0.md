# Szigyr（AIファースト言語）設計案 v0

Nov 18, 2026 · @Kw4r3n

## 要約

Szigyr は、TypeScript の構文をそのまま使い、意味を「健全なサブセット＋所有権＋権限渡し」に絞った言語。開発中は JS としてすぐ実行し、出力時は速度が要る層だけを C 経由でネイティブにコンパイルする。

コードは3つの層に分かれ、関数単位で層を選ぶ。

- **managed**（既定）: ふつうの TS に近い。常に JS エンジン上で動き、メモリは自動管理。npm を呼べる。
- **strict**: 所有権で管理し、GC も参照カウントも使わない。C を直接呼べる。
- **rt**: strict からメモリ確保とブロッキングを除いたもの。オーディオコールバック用。

設計の選別基準は一つ。「AIが書くのを助ける機能」は入れず、「他者が結果を信じるための機能」と「速度・リアルタイム性という物理的な制約」に絞る。前者はモデルの進歩で価値が消えるが、後者は消えない。

この文書は v0。まだ決まっていない箇所は、最後の「未決事項」にまとめてある。数値目標はすべて未検証の目標値。

## 決定事項

未決事項のうち7つが、2026-11-18 の回答で決まった。

| 項目 | 決定 | 設計への影響 |

| 最終形 | JS ホスト形態。単体ネイティブ形態は保留 | managed 層は常に JS エンジン上で動く。C に変換するのは strict / rt 層だけ |

## 目標と非目標

挙げてもらった理想は、すべて設計上の具体的な仕組みに対応させた。

| 理想 | この設計の答え |
| --- | --- |
| GC を局所的に捨てる | 関数単位で strict 層に切り替える。そこでは GC も参照カウントも動かない |
| ライフタイムの試行錯誤を減らす | 参照は引数にしか書けない「二級参照」にする。ライフタイム注釈は言語に存在しない |
| npm を部分的に使う | managed 層から `Js` 権限つきで呼ぶ。戻り値は境界で実行時検証する |
| C と繋ぐ | 出力が C なので、C の関数を strict 層から追加コストなしで呼べる |
| AI ファースト | 注釈は全部明示、書き方は1通り、診断は JSON。人間の読みやすさは考慮しない |
| 速度が欲しい所だけ厳密に書く | 3層の使い分け。同じファイルに混在できる |
| 一通り作れる（DAW を含む） | rt 層が「確保なし・ブロックなし」を検査で保証する。音声や GUI は C ライブラリ経由 |
| TDD とミューテーションテスト | テストは実装と同じファイル。権限渡しでモック不要。ミュータントはコンパイラが作る |
| 開発は動的言語の速さ、出力は静的言語の速さ | JS バックエンドと C バックエンド。JS での挙動を基準の意味とする |
| ビルドを軽く | 開発時はファイル単位の変換だけ。重い処理はリリース時に限る |

やらないこと。

- **人間向けの可読性や書きやすさ。** 冗長さは気にしない。
- **安定 ID と意味トランザクション。** 以前の試作で、モデルの進歩により価値が消えたため。
- **既存の TS コードがそのまま通ること。** 構文は同じだが、受理するのは健全なサブセットだけ。
- **TS の型レベル計算。** conditional types などは v0 では禁止。
- **マクロやコンパイル時実行。** v0 では入れない。

## 設計の柱

全体は6つの原則から導いている。迷ったらここに戻る。

1. **意味は変えない、絞るだけ。** 受理されたプログラムの意味は「JS として動かしたときの挙動」と定義する。新しい意味は足さず、TS から危険な部分を禁止するだけ。AI が持つ TS の知識がそのまま正しく使える。
2. **健全性を一度払って、三度使う。** 型が健全なら、証明の土台になり、型を信じた最適化ができ、開発時と出力時の挙動が一致する。
3. **所有権は「コピーか参照か」を見えなくするために使う。** 一意に所有された値と不変の値は、JS ではオブジェクト参照、ネイティブでは詰めた構造体として表現しても、挙動の違いを観測できない。だから同じソースを両方で動かせる。
4. **効果は引数で渡す。** ファイル、時刻、乱数、npm、C 呼び出しは、権限オブジェクトを受け取った関数だけが使える。大域的な権限はない。
5. **フィードバックは安い順に並べる。** 実行（ミリ秒）、型と所有権の検査（秒）、テスト、ミューテーション、証明、最適化ビルドの順。高いものほど外側のループに置き、内側を止めない。
6. **推論は関数の中だけ。** 関数の引数、戻り値、層、権限はすべて明示する。ファイル単位で並列に検査と変換ができ、関数単位で検証結果をキャッシュできる。

## 3つの層とメモリモデル

GC を「局所的に捨てる」単位は関数。関数本体の先頭に指示子を書くと、その関数は上の層の機能を使えなくなり、代わりに保証が増える。

| 層 | 指定 | メモリ管理 | できること | 主な用途 |
| --- | --- | --- | --- | --- |
| managed | なし（既定） | JS エンジンの GC | クロージャ、async、npm、可変長コレクション | アプリの大半 |
| strict | `"use owned"` | 所有権、アリーナ、プール。GC も参照カウントもなし | 値型、固定幅整数、スライス、C 呼び出し | ホットパス、データ構造 |
| rt | `"use rt"` | 確保そのものが禁止 | strict から確保・権限・再帰を除いたもの | オーディオコールバック |

呼び出しの向きは一方通行。managed は strict と rt を呼べる。strict は strict と rt を呼べる。rt は rt だけを呼べる。

### strict 層の規則

ライフタイム注釈をなくすため、参照を「二級」に制限する。

- **値は一意に所有される。** 代入、引数渡し、戻り値は所有権の移動。移動後に使うとコンパイルエラー。
- **借用は引数の型にだけ書ける。** `Ref<T>` は読み取り、`Mut<T>` は排他的な書き込み。フィールドに保存できず、戻り値にできず、クロージャに捕捉できない。借用の寿命は常に「その呼び出しの間」なので、注釈が要らない。
- **排他性の検査は呼び出し地点だけ。** `Mut<T>` で渡した値を、同じ呼び出しの他の引数に渡していないかを見る。関数をまたぐ解析は不要。
- **コピーできる型は不変、可変な型は移動のみ。** これで JS のオブジェクト参照とネイティブの値型が同じ挙動になる。

この制限は既知の設計で、Rust の作者が当初望んでいた形でもある（[Second-Class References](https://borretti.me/article/second-class-references)）。Hylo はこの方式でライフタイム注釈をなくしている（[Hylo](https://github.com/hylo-lang/hylo-lang.github.io/blob/main/index.md)、[論文](https://ar5iv.labs.arxiv.org/html/2106.12678)）。

二級参照では書けない「保存したい参照」には、退避路を3つ用意する。

| 手段 | 仕組み | 向いている場面 |
| --- | --- | --- |
| ハンドル | `Pool<T>` への世代つき添字。解放済みへのアクセスは検出される | グラフ、エンティティ、相互参照 |
| アリーナ | `using a = Arena.create(alloc)` でスコープに紐づけ、抜けるとき一括解放。中のポインタは領域ブランド型 `P<R, T>` で外に出せない | フレーム単位、リクエスト単位、構文木 |
| 明示的な参照カウント | `Rc<T>` と `Weak<T>` | どうしても共有が要る箇所 |

### rt 層の規則

- メモリ確保、権限の受け取り、managed の値への接触、再帰を禁止する。
- 引数で借りたバッファへの読み書きと、数値計算だけができる。
- トラップしうる演算（範囲外アクセス、整数の溢れ）は、v0 では許可して一覧を JSON で報告する。後の段階で、証明か明示的な分岐を要求してゼロにする。

同種の検査は Clang にもある。`nonblocking` 属性を付けた関数が、ロック待ち・ヒープ確保・例外送出をしないことをコンパイル時に調べる（[Function Effect Analysis](https://llvm.googlesource.com/llvm-project.git/+show/refs/heads/main/clang/docs/FunctionEffectAnalysis.md)）。OxCaml の `local` モード（スコープから出ない値をスタックに置く）も近い考え方（[論文](https://icfp24.sigplan.org/details/icfp-2024-papers/19/Oxidizing-OCaml-with-Modal-Memory-Management)）。

### managed 層のメモリ管理

- managed 層は開発時も出力時も JS エンジン上で動き、メモリはエンジンの GC が管理する。
- 解放のタイミングをプログラムから観測できないよう、ファイナライザは言語に入れない。資源の後始末は `using` 宣言だけで行う。
- 単体ネイティブ形態は保留。再開する場合は、参照カウント＋循環回収を第一候補にする。全体停止がなく、C として素直に出力でき、一意だと分かる値のカウント操作を省けるため。

### 例

```ts
// managed: ふつうの TS に見える
export function loadPreset(fs: Fs, path: string): Result<Preset, IoError> {
  const text = fs.readText(path);
  if (text.kind === "err") return text;
  return parsePreset(text.value);
}

// rt: 確保なし。JS では Float32Array、ネイティブではポインタと長さ
export function mixInto(out: Mut<Slice<f32>>, src: Ref<Slice<f32>>, gain: f32): void {
  "use rt";
  requires(out.length === src.length);
  for (let i: usize = 0; i < out.length; i += 1) {
    out[i] = out[i] + src[i] * gain;
  }
}

// strict: 作業領域をアリーナに置き、関数を抜けるとき一括解放
export function medianOf(alloc: Alloc, samples: Ref<Slice<f32>>): f32 {
  "use owned";
  using scratch = Arena.create(alloc);
  const work = scratch.copyOf(samples);
  sortInPlace(work);
  return work[divTrunc(work.length, 2)];
}
```

### 並行性

isolate 方式にする。isolate ごとに独立した managed ヒープを持ち、やり取りは「所有権を移した値」か「深く不変な値」のメッセージだけ。JS では Worker、ネイティブでは OS スレッドに対応する。

オーディオスレッドは rt 層だけが動く isolate で、他とはロックフリーのリングバッファで繋ぐ。

## 型システム

TS の型システムから不健全な部分を禁止し、実装に依存する部分を隠す。型検査器は自作する（tsc は使わない）。構文解析は既存の TS パーサを流用する。

| TS の機能 | Szigyr での扱い | 理由 |
| --- | --- | --- |
| `any` | 禁止。`unknown` と絞り込みだけ | 健全性 |
| `as`（`as const` 以外）、`!` | 禁止。検査つき変換 `cast<T>(x)` が `Result` を返す | 健全性 |
| 配列の添字 | 範囲検査つき。範囲外はトラップ。`get(i)` は値か `null` を返す | 健全性 |
| 関数引数の双変性、可変配列の共変性 | 引数は反変、可変コレクションは不変に固定 | 健全性 |
| 構造的部分型 | オブジェクト型は閉じた正確な型。抽象化は `interface` を明示的に実装 | 固定レイアウト |
| union | タグつき union と「値または `null`」だけ | 固定レイアウト |
| `undefined`、省略可能プロパティ | なし。`null` に一本化 | 書き方を1通りに |
| class | 継承なし、フィールド固定。動的な `this`、getter/setter、prototype 操作は禁止 | 固定レイアウト |
| `throw` / `try` | 回復不能なパニック専用。回復可能なエラーは `Result<T, E>` | 効果の明示 |
| `number` | f64。strict 層では `i8`〜`i64`、`u8`〜`u64`、`f32`、`f64`、`usize` を使い、暗黙変換なし | 速度 |
| 整数演算 | 溢れはトラップ。折り返しは `wrapAdd` などを明示。整数の `/` は禁止し `divTrunc` を使う | 両バックエンドの一致 |
| 文字列 | managed 層では JS の文字列そのまま。strict / rt 層に文字列型はない | managed 層は常に JS 上で動くため、制限が要らなくなった |
| オブジェクトの `===` | 数値、文字列、真偽値、`null`、managed 参照だけ。値型は `eq()` | 値型に同一性を持たせない |
| `for…in`、`Object.keys`、Proxy、eval、decorator、enum、namespace、overload | 禁止 | 列挙順などの実装依存を除く |
| conditional / mapped / template literal types | v0 では禁止 | 検査器を小さく保つ |
| モジュール直下の可変変数 | 禁止。`const` の不変値だけ | 大域状態をなくす |

禁止とトラップは「絞る」操作であり、計算結果を変える規則は一つもない。トラップしなかったプログラムは、JS として動かした場合と同じ値を返す。

ジェネリクスはリリース時に単相化する。開発時は JS のままなので、単相化のコストは開発ループに乗らない。

浮動小数点は IEEE 754 で両バックエンドを揃える。C 側は積和の融合と fast-math を無効にする。`sin` などの超越関数は実装差が出るため、標準ライブラリで自前実装する。

## 効果と権限

外界に触れる機能は、権限オブジェクトを引数で受け取った関数だけが使える。`console`、`Date.now`、`Math.random`、`fetch` を直接呼ぶことはできない。

`main(sys: System)` がすべての権限を受け取り、必要な部分だけを下の関数に渡す。Zig がアロケータや Io を引数で渡すのと同じ流儀を、コンパイラが強制する。

| 権限 | 許すこと | 使える層 |
| --- | --- | --- |
| `Alloc` | strict 層での動的確保 | strict |
| `Fs`、`Net` | ファイルとネットワーク | managed、strict |
| `Clock`、`Random` | 時刻と乱数 | managed、strict |
| `Log` | ログ出力 | managed、strict |
| `Js` | npm パッケージの呼び出し | managed |
| `Ffi` | C 関数の呼び出し | strict |
| `Spawn` | isolate の起動 | managed |

rt 層は権限を一切受け取れない。

この設計から、テストに効く性質が3つ出る。

- **権限引数のない関数は純粋で決定的。** 結果をキャッシュでき、並列に実行できる。
- **モックが要らない。** 偽の権限（`FakeFs`、固定時刻の `Clock`、シード固定の `Random`）を渡すだけ。
- **再生できる。** 権限の入出力を記録すれば、同じ実行を再現できる。

managed 層での暗黙のメモリ確保は、効果として追跡しない。追跡するとほぼ全関数に付いて、情報にならないため。

## 実行モデル

1つのソースから、JS と C の両方を作る。JS は開発時の全層と出力時の managed 層に、C は出力時の strict / rt 層に使う。基準の意味は JS 側にあり、C 側はそれと観測上等しくなければならない。

&#91;embedded content: 実行モデル · 共通フロントエンド、2つのバックエンド、差分テスト\]

検査は共通で、分かれるのは変換から先。破線の差分テストが、両者の一致を守る。

|  | 開発時 | 出力時 |
| --- | --- | --- |
| managed 層 | ファイル単位で JS に変換。型を消し、契約の assert を挿入 | 同じ変換結果をまとめて配布 |
| strict / rt 層 | ファイル単位で JS に変換。整数演算の検査を挿入 | まとめて C に変換し、`zig cc` か clang でコンパイル |
| 全体解析 | なし | strict / rt 層だけ（単相化） |
| 目標時間 | 1ファイル 10ms 未満 | 分単位でも可 |

型と所有権の検査は、常駐プロセスが実行と並行して行う。実行は検査を待たない。ただし検査は常に走り、結果は JSON で流れる。

### プラットフォームごとの形

最初に作るのは Linux。ブラウザとモバイルは、同じ C 出力を Wasm に向けて対応する。

|  | Linux | ブラウザ | モバイル |
| --- | --- | --- | --- |
| managed 層 | Node / Bun | ブラウザの JS エンジン | WebView の JS エンジン |
| strict / rt 層 | ネイティブアドオン | Wasm | Wasm |
| C ライブラリ | そのままリンク | Wasm にコンパイルできるものだけ | Wasm にコンパイルできるものだけ |
| 音声の rt 実行 | C ライブラリのオーディオスレッド | AudioWorklet 内の Wasm | AudioWorklet 内の Wasm |

音声出力や描画のようにホストごとに実装が違う機能は、標準ライブラリの権限（例: `AudioOut`）として抽象化し、実装をプラットフォームごとに持つ。

モバイルは未検証。WebView なら Wasm が使えるので、ブラウザ対応の延長になる。React Native の Hermes は、2026年2月時点で Wasm 対応が進行中と報じられていた（[Rocket Ship #092](https://zeno.fm/podcast/rocket-ship/episodes/092-react-native-0-84-hermes-v1-a-tanstack-react-native-framework)）。現状は未確認。

### 層の境界のコスト

JS ホスト形態では、managed 層と strict 層の境界が、JS とネイティブの境界になる。呼び出し1回ごとにコストがかかるので、境界は粗く切る。

- サンプル単位ではなく、バッファ単位で呼ぶ。
- データは共有メモリ上の型つき配列で渡し、コピーしない。
- ループの中で境界をまたぐ呼び出しは、コンパイラが診断として報告する。

### 開発時と出力時を一致させる方法

- **差が出る機能を言語から除く。** 文字列の内部表現、オブジェクトの同一性、プロパティの列挙順、ファイナライザ、整数の幅、浮動小数点の融合演算。型システムの節の禁止事項の多くは、このためにある。
- **評価順を固定する。** JS は左から右と決まっている。C 出力では一時変数に受けて同じ順序にする。
- **差分テストを標準にする。** `szigyr test --backend=both` が同じテストを両方で実行し、出力とトラップ位置を比べる。

### C を出力先にする理由

- C ライブラリをそのまま呼べる。
- C のコンパイルは速く、モジュール単位で並列化とキャッシュが効く。
- `zig cc` を同梱すれば、クロスコンパイルと Wasm 出力が追加の環境構築なしで手に入る。
- LLVM に直接繋ぐより、試作が大幅に軽い。Static Hermes も C 経由でネイティブ化している（[発表資料](https://speakerdeck.com/tmikov2023/compiling-a-real-world-cli-tool-to-native-with-static-hermes)）。

## 相互運用

### npm

npm は managed 層から `Js` 権限つきで呼ぶ。JS 側の値は信用せず、境界で検証する。

```ts
import { parse } from "npm:yaml";

export function readConfig(js: Js, text: string): Result<Config, JsError> {
  const raw = js.call(parse, [text]);      // 例外は Result に変換される
  if (raw.kind === "err") return raw;
  return js.decode<Config>(raw.value);     // 型から生成した検証器で実行時検査
}
```

- `.d.ts` は保証ではなく主張として扱う。宣言した型への変換時に、コンパイラが生成した検証器が実行時に確かめる。
- 検証したくない大きな値は、不透明な `JsRef` のまま持ち回れる。
- 例外は境界で `Result` になる。Promise は Szigyr の async に繋がる。

配布形態は JS ホスト形態を採用した。単体ネイティブ形態は保留。

| 形態 | 構成 | 状態 |
| --- | --- | --- |
| JS ホスト形態 | JS エンジンが主。strict / rt 層はネイティブアドオンか Wasm として読み込む。npm はエンジン本来の速度で動く | 採用 |
| 単体ネイティブ形態 | managed 層も C に変換し、`Js` 権限を使うプログラムにだけ JS エンジンを埋め込む | 保留 |

### C

- strict 層から `Ffi` 権限つきで呼ぶ。ネイティブ出力では直接の関数呼び出しになり、追加コストはない。
- v0 では `extern` 宣言を手書きする（AI が書く）。後で C ヘッダから自動生成する。
- 生ポインタ `Ptr<T>` を扱えるのは `"use unsafe"` を付けた関数だけ。その上に安全なラッパを書いて公開する。
- 音声入出力、GUI、GPU、コーデックは C ライブラリ経由で使う。「一通り作れる」の根拠はここにある。
- 開発時（JS 上）に C をどう呼ぶかは未決。候補は、C を Wasm にコンパイルして読み込む方法と、ホストの FFI を使う方法。

## テスト

テストの質は、カバレッジではなくミューテーションテストで測る。AI はテストを大量に書けるので、カバレッジの数字だけではテストが効いているか分からない、という参考記事の主張を前提にする（[mizchi「ミューテーションテスト」](https://zenn.dev/mizchi/articles/mutation-test-quality)）。

### 書きやすさ

- **テストは実装と同じファイルに書く。** `test("…", (t) => { … })` をモジュール直下に置く。リリース出力からは除かれる。
- **モックを書かない。** 偽の権限を渡すだけで済む。
- **性質テストを標準装備。** `forAll` の入力は型から自動生成し、`requires` を満たすものだけを流す。失敗したら最小の反例まで縮める。
- **契約がテストになる。** `ensures` を書いた関数は、ランダム入力を流すだけで検査される。
- **保存から結果までが速い。** `szigyr test --watch --json` が、変更に関係するテストだけを JS 上で再実行する。

### ミューテーションテスト

コンパイラの機能として持つ。型と層と権限の情報を使えるので、外部ツールより有利な点が多い。

| 課題 | 言語側の手当て |
| --- | --- |
| 型が通らないミュータントが無駄 | 型つき中間表現の上で変異させるので、最初から生成されない |
| ミュータントごとのビルドが遅い | 全ミュータントを1つのビルドに埋め込み、実行時スイッチで切り替える |
| 関係ないテストまで走る | テストごとの到達関数を記録し、変異箇所を通るテストだけ実行する |
| 毎回やり直しになる | 関数本体と関連テストのハッシュをキーにキャッシュする。差分実行が既定 |
| IO を含むテストは遅くて不安定 | 既定の対象は純粋関数と、偽の権限だけで動くテスト。これは型で判定できる |
| 無限ループするミュータント | 元の実行時間の数倍で打ち切る |
| 等価ミュータント | AI が理由つきで `equivalent` と印を付けられる。後の段階では SMT で等価性を示して自動除外する |
| 生存ミュータントの直し方が分からない | 元とミュータントで結果が変わる入力を、性質テストの生成器で探してレポートに添える |

最後の行がこの節の要点。生存ミュータントごとに「この入力なら差が出る」という具体例が JSON で返るので、AI はそれをそのままテストケースにできる。

記事が挙げる運用上の知見も取り込む。

- カバレッジ目標は置かない。
- 常時 CI で全件回すのではなく、関数を書き終えたときとリファクタ時に差分で回す。記事のベンチマークでは全体 12.2 秒に対し差分 0.71 秒で、AI の試行錯誤ループに入る速さになる。
- 削除しても生存した文は、デッドコード候補として別枠で報告する。
- 外部 IO を含む統合テストは対象外。そちらは権限の記録と再生で扱う。
- 設定項目を増やさない。対象の選別は型と層から自動で決める。

## 契約と検証

契約は関数本体の先頭に、組み込み関数の呼び出しとして書く。構文は TS のまま。

```ts
export function gainToDb(gain: f32): f32 {
  requires(gain > 0);
  ensures((r) => isFinite(r));
  return 20 * log10(gain);
}
```

同じ契約を、強さの違う4つの方法で使う。

1. **実行時の assert。** 開発時は常に有効。
2. **性質テストの判定基準。** `requires` が入力の条件、`ensures` が合否になる。
3. **ミュータントを殺す手段。** 契約違反もテスト失敗として数える。
4. **静的な証明。** SMT ソルバで全入力について示す。

証明は関数単位、非同期、キャッシュつきで、開発ループを止めない。失敗は反例つきの JSON で返す。

証明には速度という報酬を付ける。証明できた範囲検査、溢れ検査、契約検査は、リリースビルドから削除する。rt 層では「トラップしうる箇所ゼロ」を証明で達成できる。

v0 で実装するのは 1〜3 まで。静的証明は最後の段階に回す。strict 層は別名がないため、検証条件が単純になる。Verus が Rust の所有権を証明に利用しているのと同じ理屈（[Microsoft Research](https://www.microsoft.com/en-us/research/?p=1097610)）。TS に注釈を足して Dafny や Lean で検証する先例として LemmaScript がある（[GitHub](https://github.com/midspiral/lemmascript)）。

仕様が正しいかどうかは、言語では保証できない。緩すぎる仕様を見つけるため、契約そのものも変異させて、テストや証明が落ちるかを確かめる。

## AI 向けツール

道具は `szigyr` という1つのコマンドにまとめ、すべての出力を JSON にできる。

| コマンド | 役割 |
| --- | --- |
| `szigyr check` | 型、所有権、層、権限の検査 |
| `szigyr run`、`szigyr test` | JS 上で実行。`--backend=both` で差分テスト |
| `szigyr mutate` | ミューテーションテスト。既定は前回からの差分 |
| `szigyr prove` | 契約の静的証明 |
| `szigyr build` | C 経由のリリースビルド |
| `szigyr query` | 型、層、権限、呼び出し関係、関連テスト、生存ミュータント、トラップ箇所の問い合わせ |
| `szigyr explain <code>` | エラーコードの詳細説明 |

- **診断は構造化する。** 安定したエラーコード、位置、原因のデータ、機械的に適用できる修正候補を返す。文章は補助。
- **問い合わせ API を MCP サーバとしても公開する。** エージェントがファイルを読み直さずに事実を引ける。
- **仕様書は1ファイル。** `SPEC.md` に「TS との差分」として全仕様を書く。学習データが存在しない言語なので、これがモデルにとって唯一の教材になる。常にコンテキストに置ける長さ（目安として1万トークン以内）に収める。
- **整形器は設定なし。** 正規形は1つだけ。

入れないものは、型つきホール、安定 ID、意味トランザクション。モデルの進歩で価値が消える側の機能だと判断した。

## 試作ロードマップ

各段階は、単独で役に立つところで区切ってある。ネイティブ寄りの部分を早く実証するため、strict / rt 層と C バックエンドを前に置いた。

- **段階 0: 仕様と適合テスト。** `SPEC.md` と、受理すべき例・拒否すべき例のテスト集を先に書く。完了条件: 受理例 20 本と拒否例 50 本が揃う。
- **段階 1: 検査器と JS バックエンド。** コンパイラは TS で書く。既存パーサの流用、型と健全性の規則、権限、`szigyr test`。完了条件: 受理例がすべて Node か Bun で動き、TDD のループが回る。
- **段階 2: strict / rt 層と C バックエンド（Linux）。** 所有権の検査、C への変換、ネイティブアドオンとしての読み込み、差分テスト。完了条件: 数値カーネルが手書き C の 1.5 倍以内の時間で動き、両バックエンドの結果が一致する。
- **段階 3: C FFI、isolate、rt スレッド。** 完了条件: C の音声ライブラリ経由で音が出る。コールバックは rt 層、パラメータは managed 側からリングバッファで送る。これが DAW の最小核になる。
- **段階 4: 契約、性質テスト、ミューテーション。** 完了条件: `szigyr mutate` が差分で動き、生存ミュータントに「差が出る入力」が付く。
- **段階 5: ブラウザとモバイル。** 同じ C 出力を Wasm に向ける。完了条件: 段階 3 の音声デモがブラウザで動く。
- **段階 6: 静的証明。** 完了条件: strict 層の関数で、証明により範囲検査が消える。
- **保留: managed 層のネイティブ化。** 単体の実行ファイルが必要になったら着手する。

段階 4 は段階 2〜3 に依存しないので、並行して進められる。段階 3 が終われば、DAW のようなリアルタイム用途が作れることを実証できる。

数値はすべて目標値で、根拠のある見積もりではない。

## リスクと未決事項

### リスク

| リスク | 手当て |
| --- | --- |
| 2つのバックエンドで挙動がずれる | ずれる機能を言語から除く。差分テストを標準にする |
| managed 層のネイティブ化が大きすぎる | 保留にした。JS ホスト形態を最終形とする |
| TS に見えるせいで、AI が禁止された書き方をする | 意味は変えず禁止するだけにする。エラーに修正候補を付ける。`SPEC.md` を常に読ませる |
| 二級参照では書きにくい構造が出る | ハンドル、アリーナ、`Rc` の退避路。段階 2 で実例を書いて確かめる |
| npm 境界の検証が遅い | `JsRef` で検証を省略できる |
| モデルの進歩で一部が不要になる | 「書くのを助ける機能」を最初から入れていない。該当するのは診断の JSON 化だけ |

### 未決事項

残っているのは次の5つ。推奨案で仮決めしてある。

1. **Linux での strict / rt 層の配布形式。** ネイティブアドオンだけ（推奨。速度と C 連携のため）か、Linux でも Wasm を選べるようにするか。
2. **開発時の C 呼び出し。** C を Wasm にして読み込むか、ホストの FFI を使うか。
3. **並行性。** isolate だけ（推奨）か、共有メモリのスレッドも入れるか。
4. **モバイルのホスト。** WebView（推奨、未検証）か、React Native か。
5. **単体ネイティブ形態を再開する条件。** そのときに managed 層のメモリ管理方式も決める。
